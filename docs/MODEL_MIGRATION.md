# 模型遷移紀錄:從零訓練 char-level GPT → 微調預訓練繁體中文 GPT2

## NEXUX Model v1.0(正式起點)

**定案版本**:模型權重來自 commit `35cab73`(git tag `v1.0-model` 標在
後續補文件的 `5cc0e06`,兩者模型檔案完全相同,tag 只是晚一個commit才
補上)—— ckiplab/gpt2-base-chinese(102M 參數)微調 10000 步(約 2.5
epoch)的版本。

**版本管理更新(扶正為唯一正式版本)**:通過測試、確認比舊版穩定後,
`own_beta` 這個 Beta 標籤已經拿掉,直接扶正成 `provider == "own"` 唯一的
正式版本(不再有 `own`/`own_beta` 兩套並存)。舊版(從零訓練的
char-level 模型)不再部署、不再上傳新的權重檔案,對應的
`weights_meta.json`/`weights.npz`/`tokenizer.json` 已經從 git 追蹤中移除
(`git rm --cached`,檔案仍留在本機,git 歷史紀錄也完整保留、隨時可以
從舊 commit checkout 出來比較),舊版程式碼(`inference.py` 的
`load_model()`、`train.py`、`export_weights.py`)一樣保留在檔案裡不刪除,
純粹是不再被正式站載入。

版本管理原則:
- 正式環境只使用目前最佳版本(`own` = NEXUX v1.0)。
- 舊版本停止部署,但保留 archive 備份(本機檔案 + git 歷史)。
- 不刪除歷史紀錄,保留模型演進軌跡。
- 後續更新以 v1.0 為基礎持續迭代,不再頻繁更換底層架構。

**判定理由**:10000 步結果已經驗證訓練不足假說(見下方對照表),模型
開始展現出理解問題方向的能力(不再是完全隨機的答非所問),生成文字的
連貫性也明顯優於從零訓練的舊模型。雖然還沒有到完全答對所有問題,但
已經跨過「語言能力堪用」這個第一個重要里程碑,值得定案為正式起點,
之後的改進都基於這個版本迭代,不再大幅更換架構或訓練方式。

**之後的開發原則**:
1. 持續累積高品質 SFT 內容,擴充知識與能力(語料的質比單純堆量重要)。
2. 持續優化模型本身,改善回答的準確度、邏輯性與穩定性。
3. 保留 `eval_open_ended.py` 固定 benchmark,每次更新都要用同一組固定
   種子重新測試,確認是否真的進步,不能只憑感覺判斷。
4. **暫時不做 RLHF/DPO**——這類偏好學習方法的前提是模型已經能大致
   答對、只是需要挑出「哪個答案更好」,現在的準確度還沒到那個門檻,
   做了也只是在雜訊裡挑雜訊,效益不成比例。等基礎回答能力更成熟、
   `eval_open_ended.py` 的扣題率穩定提升後,再重新評估時機。
5. 不再頻繁更換底層模型架構——v1.0 是要「養大、養穩」的對象,不是
   隨時可以丟棄重來的實驗品。
6. 未來若進行品牌名稱調整,NEXUX v1.0 這個名稱與版本紀錄仍保留作為
   技術起點與歷史版本紀錄,不因品牌變動而被覆蓋或遺失。

## 背景與問題診斷

第十五批語料(commit `8fdc1fe`)訓練完成後,檢查訓練曲線發現嚴重過擬合:

```
step     0  train 7.98  val 7.98  gap +0.00
step   200  train 4.49  val 5.87  gap +1.37
step   600  train 3.16  val 5.19  gap +2.02
step  1200  train 2.36  val 5.10  gap +2.73  <- 最佳點
step  1800  train 1.76  val 5.19  gap +3.43
step  2200  train 1.39  val 5.35  gap +3.96  <- 早停點
```

train loss 一路下降(模型在背訓練資料),val loss 在第 1200 步後反彈上升,
train/val 差距從 0 擴大到接近 4——典型的過擬合訊號。

**根本原因**:模型 19.91M 參數,按 Chinchilla 法則大約需要 20 倍參數量的
token(~4 億)才能訓練到位,實際訓練集只有 36.6 萬 token,**差了約 1100 倍**。
這代表無論再怎麼擴充語料或調整架構,「從零訓練」這個做法都無法在合理時間內
補上這個資料量缺口——語料成長速度(每天數十到數百筆)跟需求量(數億 token)
完全不成比例。

## 決策:改用微調預訓練模型

不再「從零訓練」,改成「微調一個已經在大量語料上預訓練過的小模型」。
選用 [ckiplab/gpt2-base-chinese](https://huggingface.co/ckiplab/gpt2-base-chinese)
(中研院 CKIP Lab,專門針對繁體中文,102M 參數,GPL-3.0 授權)。

完整規劃見 `.claude/plans`(或本次對話紀錄),分三階段執行:
1. 本機可行性驗證(權重轉換 + 數值比對 + 生成品質初測)
2. 微調整合(接上現有語料跑 SFT)
3. 部署驗證(匯出格式、Vercel 上線測試)

## 舊模型 vs 新模型(未微調前)測試結果對比

測試用的是完全開放式、語料庫裡沒有的問題(排除 qa_lookup 保底機制干擾,
純測「模型生成」本身的能力)。

| 問題 | 舊模型(19.91M,從零訓練) | 新模型(102M,預訓練,尚未微調) |
|---|---|---|
| 你覺得友情跟愛情最大的差別是什麼? | 我覺得這樣,但如果真正常。 | ,因為有一點是沒什麼好處。當然也很可能會被發現那就不存在了,甚至更多人猜測他們正 |
| 如果可以回到過去,你會想改變什麼? | 我覺得這個月開心的是很多時候。 | 樣的觀念?還有很多其他的問題是:台灣經濟發展面臨許多困難;就業率不斷增加、失業人 |
| 幫我想一個關於太空旅行的故事開頭 | 對啊,真人可以讓我們去看過這樣?有趣!我會找到不錯的經驗和時候... | ,因為有了這種經驗和實際狀況可以用與地球人類聯繫。在《》中,阿拉伯神話中最古老 |

**觀察**:
- 舊模型輸出語句破碎、文法不通,幾乎看不出在回答什麼。
- 新模型(即使還沒微調成「會回答問題」的行為模式,現在是純接龍狀態)文法
  完全通順、用詞正確,甚至會帶出真實世界知識(阿拉伯神話、台灣經濟議題),
  證明它確實學過語言的通用規律,不是在硬背。
- 新模型目前的弱點是「不知道自己在回答問題」(還沒微調前是自由接龍行為),
  這是下一階段微調要解決的。

## 技術驗證(轉換正確性)

用同一段輸入(`為什麼天空是藍色的`)分別跑原始 HuggingFace 模型(torch)
與轉換後的 `numpy_gpt.py` 推理引擎,比較 logits 數值:

- 最大絕對誤差:0.000008
- 平均絕對誤差:0.000001
- 兩邊預測的下一個字完全一致(都是「,」)

結論:權重轉換正確,浮點誤差在合理範圍內。

## 已知問題 / 風險

1. **推理延遲明顯變慢**:純 numpy、無 KV-cache 的推理引擎,102M 參數模型
   (5倍於舊模型)生成速度明顯變慢,3 句測試(各 40 新 token)花了數分鐘,
   需要在部署前實測是否能在 Vercel `maxDuration: 60` 內完成回應,必要時
   優化(降低生成長度、或補上 KV-cache)。
2. **部署檔案大小**:102M 參數 float16 約 195MB,超過 GitHub 單檔 100MB
   硬限制,需要 int8 量化或分片匯出。
3. **GPL-3.0 授權**:選用的預訓練模型是 GPL-3.0 授權,需要留意衍生模型的
   授權義務(專案本身是公開 repo,基本符合公開原始碼要求)。
4. **舊模型(char-level)保留**:遷移完成前,現有 char-level 模型與規則
   系統(smalltalk.py / qa_lookup.py)持續正常運作於正式站,不受影響。

## 微調後(SFT + EOS)生成品質

第一次微調(1500 步,未教 EOS)結果:模型已經會用「答:」的口吻正經回答問題,
文法通順連貫,但不知道該在哪裡停下來,只能靠外部 `max_new_tokens` 硬性截斷。

第二次微調(重新從乾淨的預訓練 checkpoint 開始,SFT 資料的答案結尾接上
`[SEP]` 結束符號一起訓練)結果:模型學會了「自己判斷答完了」,5 題測試裡
4 題會在合理長度自然停下(2~60 個新 token 不等,不是每次都撐滿上限):

| 問題 | 生成長度 | 是否自己停下 |
|---|---|---|
| 謝謝你 | 2 tokens | 是 |
| 哈囉 | 11 tokens | 是 |
| 你覺得友情跟愛情最大的差別是什麼? | 29 tokens | 是 |
| 如果可以回到過去,你會想改變什麼? | 60 tokens | 是 |
| 為什麼天空是藍色的? | 撐滿 100 tokens | 否 |

**老實說明未完全解決的部分**:解釋型的長答案(需要鋪陳較多內容的問題)這次
微調後還沒學會可靠地收尾,可能是 1500 步、batch_size=1 的訓練量還不夠讓
模型充分學會「長答案也該有結尾」這個模式,不是這個機制本身無效。之後如果
要再改善,可以考慮加長 SFT 訓練步數,或針對長答案類型的語料額外加重。

## 固定評測基準(`eval_open_ended.py`,seed=1337)

之前的測試結果隨機取樣沒固定種子,同一個模型每次跑出來的 EOS 停止率會
不一樣(4/5 vs 8/8),不能公平比較「這次調整到底有沒有變好」。之後每次
調整語料/訓練設定,都用 `python eval_open_ended.py --pretrained` 固定種子
重跑,拿新結果跟下面這份基準比較:

```
Q: 謝謝你
A(19 tokens, 自己停下=True): 一切都能夠心情不好意思,讓我很開心。

Q: 哈囉
A(10 tokens, 自己停下=True): 嗨,謝謝你的提醒。

Q: 你覺得友情跟愛情最大的差別是什麼?
A(48 tokens, 自己停下=True): 我會盡力地表現,這樣的話讓對方能夠更有實際的溝通與回應,也很容易在彼此之間找到共同的解決問題。

Q: 如果可以回到過去,你會想改變什麼?
A(19 tokens, 自己停下=True): 對於自己的決定,我覺得是很好的決定。

Q: 為什麼天空是藍色的?
A(24 tokens, 自己停下=True): 天氣會持續影響天氣,往往比較有乾燥雨水和冰雪。

Q: 幫我想一個關於太空旅行的故事開頭
A(10 tokens, 自己停下=True): 謝謝你們這麼擔心。

Q: 你最近過得怎麼樣?
A(14 tokens, 自己停下=True): 很好像,我會找他們聊聊天。

Q: 可以給我一些關於學習新語言的建議嗎?
A(26 tokens, 自己停下=True): 這需要透過聽眾分享,能讓我們更好地表達自己或努力。
```

**這個基準的誠實評語**:EOS 停止率 8/8(格式行為已經穩定學會),但內容
準確度普遍不夠——大多數回答文法通順卻答非所問(例如「天空為什麼藍色」
答成天氣話題)。這代表接下來要進步,重點在 SFT 資料的質與量,不是訓練
步數或 EOS 機制。

## 部署延遲優化:KV-cache

實測純 numpy 推論(無 KV-cache)在這個 102M 參數模型上,每個新字要花
2.4~2.6 秒,遠超過 Vercel `maxDuration: 60` 的限制。根本原因是
`numpy_gpt.py` 原本每生成一個新字,都會把「已生成的整段文字」從頭重算
一遍,沒有快取前面已經算過的 key/value。

在 `numpy_gpt.py` 加入 KV-cache(`forward_step()` / `_attention_step()`,
搭配 `forward()`/`_attention()` 新增的選填 cache 參數):
- 數值驗證:貪婪解碼下,加了 cache 前後生成結果**完全一致**,純粹是效能
  優化,不影響任何邏輯正確性。
- 實測速度:每字時間降到 0.15~0.33 秒,快了 8~15 倍,19 個字的回答從
  48 秒降到 5.4 秒,在 60 秒限制內有餘裕。

**重複退化問題已找到原因並解決**:較長生成(60 token)出現連續重複同一個
字(例如「靛靛靛靛...」),測試後發現是 `repetition_penalty=1.3`(沿用
char-level 模型的預設值)對這個新模型懲罰力道不夠,調高到 `2.0` 後完全
解決,生成內容也更通順連貫。這個模型的建議生成參數:
`repetition_penalty=2.0`(char-level 模型維持原本的 1.5,兩者是分開設定,
不互相影響)。

## 部署策略:先做成可切換的 Beta 選項,不直接取代預設模型

內容準確度還沒驗證到位(見上面的誠實評語),直接讓所有使用者預設切換
到新模型風險太高。改成:

- `provider == "own"`:維持原本從零訓練的 char-level 模型,行為完全不變。
- `provider == "own_beta"`:新的微調預訓練模型,前端下拉選單新增
  「模型(Beta)」選項,使用者要自己選才會用到,不影響預設體驗。

smalltalk 規則、qa_lookup 保底機制對兩者都一視同仁生效(這兩層邏輯跟底層
生成模型無關)。等 own_beta 實際使用一段時間、回答品質確認穩定,再考慮
扶正成預設的 `own`。

## 訓練不足假說驗證:10000 步 vs 1500 步

SFT 資料有 4020 筆,`batch_size=1`、隨機抽樣有放回,1500 步大約只摸過
31%的訓練資料(4020筆中約1254筆),推測是內容答非所問的主因之一,不是
EOS機制或模型能力不足。拉長到 10000 步(約 2.5 epoch)重新測試固定基準
(seed=1337):

| 問題 | 1500步 | 10000步 |
|---|---|---|
| 友情跟愛情差別 | 答非所問,沒扣題 | 「我覺得各有不同,但只要花時間了解對方為什麼會這樣想」—— 直接呼應「差別」 |
| 天空為什麼藍色 | 完全答非所問(講天氣) | 「光線透過紫外線和綠帶...轉換波長的運動」—— 開始出現光線/波長等相關概念 |
| 太空旅行故事開頭 | 完全答非所問(道謝) | 「阿海醒了,大家感受到那些真實存在的小美好…」—— 真的是故事開頭的寫法 |

**結論**:訓練不足假說得到驗證,拉長訓練步數讓內容明顯更貼題,不再是
完全隨機的答非所問。但誠實地說,還沒到「答對」的程度,句子內部邏輯
仍然會跳躍不連貫(例如天空那題提到波長但推理過程兜不起來)。訓練量是
真正有效的槓桿,值得繼續投入,但這次的 10000 步還不是終點,之後可以
考慮:更多步數、改善 batch_size=1 造成的訓練雜訊(目前每步只看一筆
樣本,loss 數字跳動很大)、或加入 learning rate schedule。

## 「略過規則」開關

NEXUX.html 新增勾選框(`skipRulesToggle`),勾選後 API 請求會帶
`skipRules: true`,`api/generate.py`/`server.py` 收到後跳過
smalltalk/qa_lookup 這兩層保底機制,直接讓選定的模型(`own` 或
`own_beta`)自己生成,方便實際測試模型本身面對簡單輸入(例如「哈囉」)
時的真實能力,不被規則搶先攔截。預設不勾選,不影響一般使用體驗。

## 已知弱點:多輪對話上下文使用能力差

實測發現:上下文組裝機制本身正常運作(`build_context_prompt()` 有正確把
歷史對話組進 prompt,例如「問:我叫小明\n答:你好小明,很高興認識你。\n
問:我叫什麼名字?\n答:」),但模型完全沒有參考這段上文,生成出無關的
內容(答不出「小明」)。這不是傳輸/串接的 bug,是模型能力沒學到「怎麼用
上文回答」這件事。

推測原因:SFT 訓練資料裡真正需要「參考上文」的多輪對話語料
(`chat.jsonl`)只有 419 筆,佔全部約 4000 多筆訓練資料的一小部分,
大部分是不需要上文的單輪 QA,模型看過的「上下文範例」明顯不夠多。

**下一批語料的優先方向**:多寫「後面的問題必須參考前面對話才能答對」的
多輪範例(例如「我叫XX」→「你好」→「我剛說我叫什麼?」這種),而不是
繼續加單輪 QA,直接針對這個已知弱點補強。

## 〔更正〕上下文語料假說驗證:先前「未驗證成功」的結論是無效的

**這一節原本記錄「15 筆上下文語料、假說未獲驗證」,後來發現整個實驗
根本沒有驗證到任何東西,原始結論予以撤回,原因記錄如下,引以為戒。**

**根本原因(pipeline 漏洞)**:`run_pretrained_sft.py` 實際上讀取的訓練
資料是 `sft_data.jsonl`,一份由 `prepare_sft_data.py` 從 `data/*.jsonl`
預先展開出來的中繼檔案,**不是**直接讀 `data/*.jsonl`。但當時(以及
之後很長一段時間)CLAUDE.md 記錄的 NEXUX v1.0 官方重訓流程裡,完全
漏掉了「新增語料後要先重新執行 `python prepare_sft_data.py`」這一步。

實際查證:當時的 `sft_data.jsonl` 是同一天早上 09:24 產生的,而加入
15 筆上下文語料的 commit(`chat.jsonl` 419→434)是下午 14:59 才提交,
足足晚了快 6 個小時。也就是說,那次「10000 步重訓」用的還是舊的、
完全不含這 15 筆新語料的 `sft_data.jsonl`——整次重訓只是拿同一份沒變
的資料重跑一次(換了隨機種子而已),15 筆新語料自始至終沒有真正被
模型看過。原本記錄的「三個測試案例全部失敗」不是「驗證了假說不成立」,
而是「根本沒驗證到任何東西」,兩者結論的可信度完全不同,不應該混為
一談。

更嚴重的是,**這個漏洞不會產生任何錯誤訊息**——`run_pretrained_sft.py`
照樣正常執行、loss 照樣正常下降、`checkpoint_pretrained.pt` 照樣正常
更新,表面上看起來完全正常,只是訓練內容悄悄地跟語料庫脫節,非常
容易被忽略,是這次事件最值得警惕的地方。

**教訓**:自動化重訓流程裡,任何「資料 A 要先手動轉換成資料 B,
訓練程式才會讀資料 B」的中繼步驟,都應該盡量讓訓練程式自動偵測
資料 A 有沒有比資料 B 新(例如比對檔案更新時間),過期就自動重新
產生,而不是完全仰賴使用者自己記得手動執行,不然這種「靜默失效、
沒有任何錯誤訊息」的漏洞很容易一犯再犯。

## 第十六批語料 + 上下文假說「真正」的第一次測試結果

修好上面的 pipeline 漏洞後,重新產生了正確的 `sft_data.jsonl`(4020→4291筆,
真的包含第十五批的 15 筆上下文語料,以及第十六批新增的 117 筆
JS/CSS/程式設計基礎/錯誤排查/邏輯推理/HTML/Python自然問答/多輪問題解決對話),
用乾淨 checkpoint 重跑一次完整 10000 步訓練。這是這兩批語料第一次真正
被訓練到,結果如下,誠實記錄,不誇大也不隱藏瑕疵。

**固定 benchmark(`eval_open_ended.py --pretrained`,seed=1337)**:EOS
自行停下比率 8/8,跟原始基準持平,內容流暢度也大致持平,沒有觀察到
明顯退步。

**上下文記憶測試(小明/藍色/25→26歲)**:

| 測試 | 這次的回覆 | 跟之前(未生效那次)的差異 |
|---|---|---|
| 姓名記憶 | 「剛說你叫大華」 | 開始使用「剛說你叫...」這種正確的指涉句型,但填入的名字是錯的(該是小明) |
| 喜好記憶 | 「你剛說了解他們看到它本身就能得輕鬆多穿一點嗎?」 | 同樣出現「你剛說」的指涉句型開頭,但後面內容不連貫,沒有正確提到藍色 |
| 資訊更正 | 「沒關係; }」 | 完全沒有回答年齡,而且出現「; }」這種類似程式碼語法的殘留字元 |

**誠實的解讀**:這是「部分訊號,不是乾淨的成功」。正面的部分是,模型
第一次開始模仿「剛說.../你剛說...」這種需要回頭參考上文才會用的句型
結構,跟先前完全無視上文、答非所問的狀況有本質上的不同,說明語料
確實在往正確的方向起作用;但模型還沒學會把句型正確套用到「對的那個
事實」上(小明講成大華、藍色沒答對、年齡完全沒答),代表這個能力
還在很初期的階段,不能說「解決了」。另外在資訊更正這題觀察到疑似
程式碼語法殘留(「; }」),額外測了 4 個跟程式完全無關的一般問題
(天氣、運動、推薦書、你會做什麼),都沒有出現類似殘留,判斷這不是
廣泛污染,比較像是多輪上下文情境下的個案,但值得之後持續留意——這次
同時混入了大量程式相關語料(JS/CSS/troubleshooting),不能完全排除是
模型容量有限,新增的程式語料佔用了原本用在其他任務上的表徵能力。

**判定:整體没有退步、且上下文能力有第一次觀察到的正向訊號(雖然還不
完整),語料本身(JS/CSS/程式設計基礎/錯誤排查/邏輯推理等 117 筆新
內容)是這次批次的主要目的且沒有被固定 benchmark 偵測到任何負面影響,
予以匯出部署。** 上下文事實綁定能力仍是已知弱點,留給下一批語料繼續
處理,不會因為這次的部分訊號就宣稱已解決。

## 補齊語料缺口批次(HTML5語意標籤/文章排版/JS表單驗證/3則多輪對話,8筆)

延續上面的方向,補上使用者原始規格裡幾個還沒真正覆蓋到的類別(HTML5語意
化標籤、文章排版、JavaScript表單驗證),外加3則多輪對話情境,用正確

**固定benchmark**:EOS自行停下比率8/8,跟基準持平,內容流暢度也大致
持平,沒有觀察到退步。

**上下文記憶測試(小明/藍色/25→26歲)再測一次**:結果跟上一輪一樣是
混合訊號,沒有更好也沒有更差——姓名記憶這次完全答非所問(甚至出現
「程式碼」字眼的離題內容,比上一輪的「剛說你叫大華」還要離題);喜好

## 第十七~十九批語料(92筆)重訓:EOS 停止率退步,沒有部署

這批是目前為止單次新增量最大的一批(29則多輪對話+HTML/Python/CSS/JS
自然問答共92筆),`sft_data.jsonl` 自動重新產生為4442筆,用乾淨checkpoint
重跑10000步。

**固定benchmark結果:EOS自行停下比率從基準的8/8降到6/8**(「為什麼天空
是藍色的」「太空旅行故事」兩題都生滿100 token沒有自然停止)。這是一個
用同一套固定benchmark方法量到的明確退步,不是含糊的主觀判斷。內容本身
流暢度沒有明顯變差(「天空為什麼藍」這題甚至提到「散射」「大氣」這種
確實跟主題相關的物理概念),但EOS機制的退步是清楚可量測的事實。

上下文記憶測試(小明/藍色/年齡更正)維持先前幾輪的混合訊號模式,沒有
新的觀察。

**判定:EOS停止率退步達到需要謹慎對待的程度,這次不予部署。**
`weights_pretrained.npz` 已用 `git checkout` 還原回上一個確認良好的版本
(補齊語料缺口那批,EOS 8/8)。這批92筆語料的內容本身沒有理由相信有
問題(HTML/CSS/JS/Python的自然問答風格跟先前驗證過的批次一致),比較
可能的原因是這次新增的資料量是先前最大的一次,加上 SFT 訓練本身
`batch_size=1`、每步隨機抽樣造成的變異。

**〔更正〕原本這裡寫「seed是寫死的1337,同樣指令重跑會得到完全一樣的
結果,要排除隨機性得換seed」,這句話後來發現是錯的**,已經回頭讀
`dataset.py` 確認:`SFTDataset.get_batch()` 實際上是用 Python 內建的
`random.choice()`(dataset.py:130)決定每一步抽到哪一筆訓練樣本,不是
`torch.manual_seed(config.seed)` 控制的範圍(那個只影響 PyTorch 自己的
RNG,例如dropout);整個程式碼庫裡沒有任何地方呼叫過 `random.seed()`,
所以 Python 的 `random` 模組本身是每次執行都用不同的系統隨機性初始化。
也就是說,**同一支指令重跑,資料抽樣順序本來就會不一樣**,不需要額外
帶 `--seed` 參數才能得到不同結果——直接重跑就是在測「這次的退步是不是
隨機噪音」最直接的方法,之前的說法反了。`run_pretrained_sft.py` 仍然
保留了新增的 `--seed` 選項(可以額外控制 PyTorch RNG 的那一小部分
隨機性),但不是這裡真正需要的工具。
